# Determinism: float math is correctly rounded, pinned to CORE-MATH

fast3d promises identical results on every platform and compiler. Basic arithmetic gets
there through IEEE-754. A libm function does not: each vendor's sinf, atan2f or expf rounds
its own way. This policy closes that gap. Glenn approved it on 2026-10-17, with CORE-MATH as
the bit-exact reference.

## The rule

**(a) Correctly rounded functions.** Every float transcendental or root function the
library calls returns the correctly rounded result, round to nearest even. It is either the
CORE-MATH function at the pinned commit, or our own code proven equal to it on the harness
sets. A correctly rounded result has exactly one right answer, so it is the same on every
platform and compiler.

**(b) The basic operations are already correct.** IEEE-754 requires `+ - * /` and `sqrtf` to
be correctly rounded, and they stay deterministic under the `-ffp-contract=off` the build
sets (and `/clang:-ffp-contract=off` for clang-cl). So `sqrtf` is the hardware operation. The
reference for its row is `(float)sqrt((double)x)`. Rounding twice does no harm for square
root, because 53 >= 2*24 + 2.

**(c) `1.0f / sqrtf(x)` is two operations, not a function.** It is two correctly rounded
operations in a row, so it is deterministic, and this rule does not cover it. It is not the
correctly rounded reciprocal square root. Measured at BASE 80284fa against `cr_rsqrtf`: maxulp=1,
with 556013448 mismatches out of 2139095039 inputs (26%), worst at x=0x1.8p-148. Swapping it for
`cr_rsqrtf` would be a separate decision. Under this policy the idiom stays as it is.

**(d) No direct libm transcendental.** Nothing under `src/` or `include/` calls a libm
transcendental directly. To use acos, exp, log or any other such function, add its CORE-MATH
file at the pin to `extern/core-math/` (through `tools/revendor-core-math.sh`) and add a
harness row for it.

## The rows

| function | row | bound (ulps) | owning card |
|---|---|---|---|
| `sqrtf` | sqrt | 0 | cm-fast3d-policy |
| `b3Atan2` | atan2 | 0 | cm-fast3d-atan2-sincos |
| `b3ComputeCosSin` | sincos | 0 for both outputs | cm-fast3d-atan2-sincos |

`./bin/test CoreMathTest` runs the rows. A row that has not landed prints
`core-math row=<name> pending: <card>`.

## Measurements at BASE 80284fa

Taken on hetzner1 (gcc 13.3, -O2 -ffp-contract=off), against CORE-MATH at the pin:

- sqrtf against (float)sqrt((double)x): maxulp=0, checked exhaustively over all 2139095040
  non-negative finite floats.
- 1.0f/sqrtf(x) against cr_rsqrtf: maxulp=1, 556013448 mismatches of 2139095039 (26%), worst
  x=0x1.8p-148.
- b3Atan2 against cr_atan2f: maxulp=591, maxabs 2.79e-05, 19229466 mismatches of 50070532.
- b3ComputeCosSin against cr_sinf/cr_cosf, every 4th float with |x|<=100: maxabs 0.00162 on
  both outputs. For |x|>100, maxabs 2, because b3UnwindAngle loses the angle in float.
- acosf, expf, logf: never called under src/ or include/.

## The pin

CORE-MATH (https://core-math.gitlabpages.inria.fr/, MIT) at commit
cac142bc65dc140d645ba3f79511a9c591d1746e of https://gitlab.inria.fr/core-math/core-math.git,
committed 2026-10-01. `extern/core-math/` holds atan2f.c, sinf.c, cosf.c and LICENSE. They
compile into libbox3d as an object library with warnings silenced on those three files only,
and they define `cr_atan2f`, `cr_sinf` and `cr_cosf`, which are not declared in `include/`.
The tree is generated by `tools/revendor-core-math.sh` and never edited by hand:

- `tools/revendor-core-math.sh` fetches the sha, copies the four files, applies
  `extern/core-math/patches/*.patch` and writes `extern/core-math/NOTES.md`, which holds the
  sha256 of each file and the reason for each patch.
- `tools/revendor-core-math.sh --check` regenerates the tree in a temp dir and exits 1 on drift.
- `tools/revendor-core-math.sh --prove` builds the patched files with gcc on the MSVC fallback
  paths and compares them with unpatched CORE-MATH: all 2^32 inputs each for sinf and cosf,
  and 2^28 input pairs for atan2f. It exits 1 if a single output differs.

MSVC cl has no GCC builtins and no `unsigned __int128`. For cl only, the build force-includes
`extern/core-math/patches/core_math_compat.h`, which maps the builtins to the C99 functions and
provides a 64x64->128 product, and the two patches route sinf and cosf through it. gcc, clang,
clang-cl, MinGW and emscripten compile the upstream code paths unchanged.

## The harness

`test/core_math_harness.h` is shared by every row:

- **ulp distance.** Measured on ordered integers. +0 and -0 count as equal only when their bit
  patterns match, and NaN equals NaN.
- **Random inputs.** A xorshift64 with the fixed seed 0x9E3779B97F4A7C15, never seeded from the
  clock.
- **Hard cases.** Every 2^10th subnormal plus the smallest and largest; the 64 floats either
  side of the float nearest k*pi/2, for k in -64..64; the 64 largest finite floats; the powers
  of two 2^20..2^127; zeros, infinities and NaN.
- **One row runner.** It prints `core-math row=<name> inputs=<n> maxulp=<m> bound=<b> worst=<input>` and fails when maxulp > bound.

The default (CI) size is the hard cases plus a dense set of at least 2^20 inputs per row. The
whole suite must take under 2 s. Setting `B3_CORE_MATH_EXHAUSTIVE=1` runs every float bit
pattern on a univariate row, and 2^28 inputs on a bivariate row.

`CoreMathWitnessTest` is the reversed witness. It plants a one-ulp error at exactly one input,
first a hard case and then a dense input, and requires the runner to go red with maxulp=1.

A row card adds one file, `test/core_math/<row>.c`, and touches nothing else.
`test/CMakeLists.txt` defines `B3_CORE_MATH_ROW_<STEM>=1` for each file present, and
`test/test_core_math.c` then runs that row's subtest.
